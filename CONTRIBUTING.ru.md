# Как участвовать в TRANSFLUX

Спасибо за интерес к проекту. TRANSFLUX — открытая парадигма, и вклад может принимать разные формы.

---

## Языки

Живая документация билингвальна. `README.md` — английский, потому что его показывает Git по умолчанию. Русская пара пишется параллельно:

| English | Русский |

## Виды вклада

### Документация и концепции

- **Новый use case** — проработанный сценарий применения трёх осей к конкретной задаче. Формат: см. `docs/ru/TRANSFLUX_Use_Cases.md` и `docs/en/TRANSFLUX_Use_Cases.md`.
- **Design rationale** — обоснование нового проектного решения или пересмотр существующего. Формат: DR-NNN в design rationale, оба языка.
- **Формальный инвариант** — новое доказуемое / тестируемое свойство системы. Формат: INV-X / OP-X / CP-X в формальных инвариантах, оба языка.
- **Сравнение с парадигмой** — честное сопоставление TRANSFLUX с ещё не описанной парадигмой или технологией. Формат: секция в документе о смежных парадигмах, оба языка.

### Спецификация

- **Уточнение формализма** — более строгая формулировка, исправление ошибок в формулах, уточнение семантики.
- **Новая производная концепция** — если выводится из трёх осей (критерий полноты §6 спецификации).
- **Пересмотр базиса** — если найден фундаментальный вопрос, не покрываемый тремя осями. Это серьёзная заявка, требующая аргументации.

### Реализация

- **Прототип на новом языке** — Rust, Haskell, Julia и др. Такие эксперименты приветствуются; текущий носитель парадигмы — Python-библиотека.
- **Библиотека** — NoisyFloat, FluxVar или SurvivalState как отдельный пакет.
- **Интеграция** — обёртки для PyTorch, TensorFlow, edge-AI фреймворков. На дорожной карте они отложены, пока проверка концепции их не потребует.
- **Тесты** — реализация тестовых спецификаций из формальных инвариантов.

## Стандарты качества

### Для документации

- Без маркетинговых утверждений без доказательной базы (нельзя: «100× быстрее»; можно: «теоретически может быть эффективнее — требует валидации»).
- Разделение регистров: манифест — для голоса, спецификация — для формализма, paradigm — для объяснений. Не смешивать.
- Явно указывать, является ли идея частью Core или исследовательским бэклогом.
- Обе языковые версии выходят вместе.

### Для кода

- Код в спецификации — иллюстративный (Python, читаемость > производительность).
- Код реализации — с тестами, покрывающими инварианты из Formal Invariants.
- Каноническое API — то, что экспортирует пакет `transflux` (`FluxVar`, `NoisyFloat`, `SurvivalState`, `TransfluxSystem`, `FlowingTrit`, `weighted_mean`, `classify_jump`, `PolyphonicIdentity`). Другие имена — алиасы или эксперименты.

### Локальная проверка

Библиотека лежит в `src/transflux/`, тесты — в `tests/` (инварианты и `tests/synthetic/`):

```
pip install -e .[dev]
pytest
```

PR, меняющий реализацию, должен проходить все тесты; PR, меняющий инварианты, должен обновить соответствующие тесты.

## Процесс

1. Откройте issue с описанием предлагаемого вклада.
2. Обсудите подход до начала работы (особенно для изменений в спецификации).
3. Создайте pull request с изменениями.
4. Каждый PR обновляет затронутые документы на обоих языках. Если меняется спецификация — обновить инварианты; если добавляется use case — проверить согласованность с текущей спецификацией.

---

## Чего мы не принимаем

- Изменения, которые нарушают ортогональность трёх осей без обоснования пересмотра базиса.
- Необратимые или деструктивные операции без явной политики Consent-First.
- Утверждения о производительности без бенчмарков.
