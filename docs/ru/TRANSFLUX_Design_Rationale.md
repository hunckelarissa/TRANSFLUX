# TRANSFLUX: Design Rationale

> Обоснование ключевых проектных решений.  
> Для каждого решения: контекст, альтернативы, аргумент.

---

## DR-001. Три оси, не две и не четыре

**Контекст.** Почему именно три оси — State, Value, Survival? Почему не добавить Logic, Identity, Time как отдельные оси?

**Решение.** Три оси = минимально полный базис.

**Аргумент.**

*Ортогональность:* ни одна ось не сводится к другой. FluxVar может работать без NoisyFloat (точное значение с историей). NoisyFloat может работать без FluxVar (точечное значение с uncertainty). SurvivalState может работать без обоих (внешний threat_level).

*Полнота:* каждая предложенная четвёртая ось выводится из существующих трёх:
- Logic (Gradient of Truth) → производная от NoisyFloat.gradient_of_truth()
- Identity (Polyphonic Identity) → производная от SurvivalState.identity_hash
- Time → встроен в FluxVar.history и FluxVar.velocity

*Необходимость:* удаление любой оси оставляет фундаментальный вопрос без ответа:
- Без State → нет модели изменения
- Без Value → нет модели неуверенности
- Без Survival → нет модели поведения под угрозой

**Статус.** Рабочая гипотеза. Если обнаружится вопрос, не покрываемый тремя осями и не выводимый из них, базис должен быть пересмотрен.

## DR-002. min() для propagation of confidence

**Контекст.** При операциях над NoisyFloat как комбинировать confidence двух операндов?

**Решение.** `result.confidence = min(a.confidence, b.confidence)`.

**Альтернативы.**

| Стратегия | Формула | Плюсы | Минусы |
|---|---|---|---|
| min (weakest link) | min(c₁, c₂) | Консервативна, проста | Может быть слишком пессимистичной |
| Мультипликативная | c₁ × c₂ | Учитывает независимость | Предполагает независимость, которая не всегда есть; быстро схлопывается к 0 |
| Байесовская | f(c₁, c₂, prior) | Наиболее корректна | Требует prior; слишком сложна для примитива |

**Аргумент.** Для примитива типа важнее предсказуемость и безопасность, чем точность. min() гарантирует, что confidence результата никогда не превышает confidence худшего операнда — это консервативно, но не лжёт. В конкретных domain-реализациях стратегию можно переопределить.

## DR-003. decay_rate по умолчанию = 0

**Контекст.** Без затухания threat_level монотонно растёт. Система гарантированно войдёт в panic при любой ненулевой угрозе — это «параноидный» режим.

**Решение.** По умолчанию decay_rate = 0. Затухание включается явно.

**Аргумент.** В модели выживания безопаснее ошибиться в сторону избыточной бдительности. Оптимистичный default (угроза рассасывается сама) может привести к тому, что реальная угроза «протечёт» через мелкие дельты, ни разу не достигнув порога. Параноидный default заставляет разработчика осознанно выбрать decay_rate, подходящий для его контекста.

## DR-004. comfort — скаляр [-1, +1], а не вектор

**Контекст.** Comfort отражает «самочувствие» системы. Это может быть многомерной величиной: комфорт по скорости, по стабильности, по нагрузке.

**Решение.** Скаляр ∈ [-1, +1]. -1 = дисфория, 0 = нейтрально, +1 = эйфория.

**Аргумент.** Для Core-примитива скаляр достаточен: он позволяет пороговые решения (`if comfort < -0.5: ...`) и передачу в другие оси. Многомерный comfort добавляет сложность (размерность? нормализация? какие измерения?), не решая задач, которые скаляр не решает на уровне ядра. Расширение до `ComfortVector` — предмет будущих версий, если практика покажет необходимость.

---

## DR-005. trauma_threshold — одно число, а не функция контекста

**Контекст.** Порог «травмы» — скорость изменения, при которой система сигнализирует об аномалии. Порог может зависеть от контекста: днём одно, ночью другое.

**Решение.** Одно число (float), модифицируемое в runtime.

**Аргумент.** Простота, детерминизм, тестируемость. Один порог легко верифицировать: «при velocity > 10.0 → trauma». Контекстная функция (`trauma_threshold = f(time, load, history)`) может быть реализована вызывающей стороной, обновляющей порог перед каждым циклом. Базовый примитив не должен содержать логику, которую проще выразить снаружи.

## DR-006. Ring buffer maxlen=32 для history

**Контекст.** FluxVar хранит историю состояний в кольцевом буфере. Какой размер?

**Решение.** 32 элемента по умолчанию, настраиваемо.

**Аргумент.** Trade-off: памяти хватает для обнаружения паттернов (тренд, осцилляция, возврат к предыдущему состоянию) в большинстве временных рядов. При частоте обновления 1/с — это 32 секунды контекста. При 1/мин — ~30 минут. Степень двойки не принципиальна для Python, но удобна при потенциальном переносе на embedded/Rust. Для конкретных доменов maxlen настраивается при создании FluxVar.

## DR-007. Panic детерминирован, а не вероятностен

**Контекст.** Можно ли сделать panic вероятностным: «при threat=0.8 — 30% шанс panic»?

**Решение.** Нет. Panic строго детерминирован: threat ≥ threshold → panic. Всегда.

**Аргумент.** Panic — это **гарантия безопасности**. Она должна быть:
- *Воспроизводимой* — одинаковый вход → одинаковый результат;
- *Тестируемой* — unit test может проверить, что при threat=0.75 и threshold=0.75 panic срабатывает;
- *Предсказуемой* — в ситуации реальной угрозы нельзя зависеть от генератора случайных чисел.

Вероятностный panic превращает гарантию безопасности в азартную игру. Это противоречит основному принципу Survival Model.

## DR-008. FluxVar.update принимает new_value, а не target

**Контекст.** Ранний эксперимент (`research/notes/TRANSFLUX.py`) использовал пружинную модель: FluxVar имел поле `target`, и значение «стремилось» к цели через пружинную динамику с ускорением и демпфированием.

**Решение.** Спецификация v0.2 использует прямой `update(new_value)`: вызывающая сторона передаёт новое значение, FluxVar фиксирует delta, velocity, acceleration.

**Альтернатива.** Target-based: `set_target(target)` + `tick(dt)` — FluxVar сам плавно движется к цели.

**Аргумент.** `update(new_value)` — более общая модель. Она не навязывает физику сходимости (пружина, демпфер, экспонента). Вызывающая сторона решает, какова траектория. Target-based модель — частный случай, который можно построить поверх `update()`:

```python
def tick_towards_target(flux, target, dt, spring_k=0.5):
    error = target - flux.value
    new_value = flux.value + spring_k * error * dt
    flux.update(new_value, dt)
```

Базовый примитив не должен ограничивать пространство возможных динамик.

## DR-009. NoisyFloat хранит σ (std dev), а не σ² (variance)

**Контекст.** Uncertainty можно хранить как стандартное отклонение (σ) или как дисперсию (σ²).

**Решение.** Хранится σ (std dev).

**Аргумент.**

| Хранение | Плюсы | Минусы |
|---|---|---|
| σ (std dev) | Читаемость: «5.0 ± 0.3» интуитивно; единицы совпадают с value | Propagation через сложение/вычитание требует σ² → одно возведение в квадрат |
| σ² (variance) | Propagation эффективнее: σ²_z = σ²_a + σ²_b без sqrt | Нечитаемо: «5.0 ± 0.09» — в каких единицах? Единицы не совпадают с value |

Для концептуального примитива читаемость важнее микрооптимизаций. `NoisyFloat(5.0 ± 0.3)` — это высказывание, которое понятно без пояснений.

## DR-010. Оси ортогональны, но связаны (coupled)

**Контекст.** Ортогональность обычно подразумевает независимость. Но в TRANSFLUX оси взаимодействуют: uncertainty влияет на threat, velocity влияет на threat, panic сбрасывает state.

**Решение.** Ортогональность ≠ независимость. Оси ортогональны по определению (не сводятся друг к другу), но связаны по поведению (coupling rules).

**Аргумент.** Аналогия: в физике электрическое и магнитное поля — ортогональные компоненты, но связаны через уравнения Максвелла. Изменение одного порождает другое. Именно связь порождает emergent-поведение (электромагнитная волна).

В TRANSFLUX связь осей порождает самонаблюдающую систему: нестабильность в одной оси (высокая uncertainty, резкая velocity) автоматически повышает бдительность в другой (threat_level). Без связи оси — просто три независимых библиотеки. Со связью — динамическая система.

Правила связи (coupling rules) зафиксированы в спецификации §4 и являются такой же частью ядра, как сами оси.

## DR-011. Consent-First для деструктивных операций

**Контекст.** Panic может уничтожить данные и сменить идентичность. Должно ли это происходить автоматически?

**Решение.** Деструктивные операции требуют явной политики. Нет дефолтного «да».

**Аргумент.** Автоматическое уничтожение данных без явной политики — это побочный эффект, маскирующийся под безопасность. В реальной системе уничтожение данных может быть катастрофой (медицинские записи, юридические документы). Consent-First означает: разработчик явно определяет, что именно уничтожается при panic, в каком scope и при каком threshold — и берёт на себя ответственность за это решение.

## DR-012. Одна формула для парадигмы

**Контекст.** Нужна ли «одна строка», описывающая всю парадигму?

**Решение.** `TRANSFLUX = Flow(State) · Uncertainty(Value) · Adaptation(Survival)`

**Аргумент.** Формула выполняет три функции:
1. *Мнемоника* — запоминается с одного прочтения.
2. *Критерий полноты* — любую новую идею можно проверить: выводится ли она из одного из трёх членов?
3. *Оператор · (произведение)* — не +, а ·. Оси не складываются (аддитивность = необязательность), а перемножаются (мультипликативность = необходимость каждого). Система без любого из трёх множителей обнуляется.

Выбор символа · — осознанный: он подчёркивает, что удаление одной оси обнуляет всю парадигму.

## DR-013. Trauma и panic — advisory, не blocking

**Контекст.** Может ли trauma_threshold или on_trauma callback заблокировать `FluxVar.update()`? Может ли panic быть отменён?

**Решение.** Нет. Оба события — **advisory**: они сигнализируют, но не отменяют операцию.

**Аргумент.**

- `FluxVar.update()` **всегда** устанавливает новое значение. Trauma callback вызывается до присвоения, но не может его предотвратить. Это гарантирует INV-F4: `value == new_value` после update.
- `SurvivalState._panic()` **всегда** сбрасывает threat и ротирует identity. on_panic callback вызывается после перерождения, но не может его отменить. Это гарантирует INV-S2 и INV-S5.

Если callback мог бы заблокировать операцию, примитив перестал бы быть предсказуемым: поведение зависело бы от внешнего кода. Это нарушает принцип детерминизма (DR-007) и делает инварианты недоказуемыми.

Callbacks **могут** иметь побочные эффекты (логирование, эскалация в SurvivalState, уведомление orchestrator-а), но поток управления внутри примитива — безусловный.

## DR-014. Orchestrator pattern для связи осей

**Контекст.** Как три оси связываются? Автоматически (внутренние ссылки) или явно (внешний orchestrator)?

**Решение.** Явный orchestrator. Примитивы не знают друг о друге.

**Аргумент.**

*Ортогональность:* если SurvivalState содержит ссылку на FluxVar, они перестают быть ортогональными — Survival зависит от State.

*Тестируемость:* каждый примитив тестируется изолированно. FluxVar не нужен SurvivalState для unit-теста.

*Гибкость:* orchestrator решает:
- какие оси связывать (не все системы используют все три);
- в каком порядке обновлять;
- что делать с fallback после panic;
- какие sensitivity параметры использовать.

Паттерн `TransfluxSystem` (спецификация §4.2) — рекомендуемый, но не обязательный. Вызывающий код может связывать оси напрямую.

## DR-015. Пакетная структура: один модуль с тремя классами

**Контекст.** Как организовать код реализации?

**Решение.** Один пакет `transflux` с подмодулями:

```
transflux/
├── __init__.py          # реэкспорт: FluxVar, NoisyFloat, SurvivalState
├── state.py             # FluxVar
├── value.py             # NoisyFloat
├── survival.py          # SurvivalState
└── system.py            # TransfluxSystem (orchestrator)
```

**Аргумент.**

- Один пакет (`pip install transflux`) — минимальный порог входа.
- Подмодули по осям — чистое разделение, ортогональность отражена в структуре.
- `system.py` отделён от примитивов — orchestrator необязателен.
- `__init__.py` реэкспортирует три класса: `from transflux import FluxVar, NoisyFloat, SurvivalState`.

**Альтернатива.** Три отдельных пакета (`transflux-state`, `transflux-value`, `transflux-survival`). Отвергнута: усложняет установку, versioning, и разрывает coupling protocol.

## DR-016. min() остаётся стратегией библиотеки

**Контекст.** Открытый вопрос §8: оставить `min` или перейти к мультипликативной / байесовской передаче confidence.

**Решение.** В Python-библиотеке остаётся `min`. Другие стратегии не реализуются, пока практика библиотеки не покажет, что слабого звена мало.

**Аргумент.** Простота и предсказуемость важнее более тонкой формулы, которую ещё не на чем проверить. DR-002 этим не отменяется, а закрывается как вопрос.

---

## DR-017. В FluxVar нет слоя constraints

**Контекст.** Черновики записывали состояние как `(value, velocity, history, constraints)` и спрашивали, должен ли примитив сам отвергать недопустимые значения.

**Решение.** Не должен. Допустимость `value` задаёт программист.

**Аргумент.** Проверка внутри русла сделала бы примитив опекуном вызывающего кода. TRANSFLUX в этом месте ближе к ассемблеру: неверное значение — ошибка того, кто его записал. Библиотека считает velocity и хранит историю; она не решает, «имеет ли право» число быть таким.

Поле `comfort` по-прежнему лежит в `[-1, +1]` — это определение самого поля (INV-F1), а не политика допустимых значений payload.

## DR-018. FlowingTrit — float, не дискретная тройка

**Контекст.** Трит можно было оставить множеством `{-1, 0, +1}` и рисовать переход между метками отдельно.

**Решение.** Состояние само есть число с плавающей точкой. `-1`, `0`, `+1` — полюса смысла. `-0.5` — полноценное значение. Клампа к отрезку `[-1, 1]` нет (см. DR-017).

**Аргумент.** Дискретная тройка снова притворяется, что между «нет», «может быть» и «да» пусто. Непрерывный трит как раз про это «между». Вектор перехода — `velocity` у `FluxVar[FlowingTrit]`, а не скрытая координата рядом с меткой.

## DR-019. Сначала Python-библиотека

**Контекст.** Дорожная карта звала сразу в DSL/LUMEN, Rust и нейроморфное железо.

**Решение.** Носитель парадигмы сейчас — пакет `transflux` на Python и оркестратор `TransfluxSystem`. Оператор `~>` в синтаксисе языка не делается: в библиотеке это метод `flow()`. DSL, LUMEN и Rust отложены. Бенчмарки, нейрочипы и исследовательский бэклог тоже отложены — концепция ещё не проверена кодом, которым можно пользоваться.

**Аргумент.** Пока три оси нельзя собрать в обычном Python и посмотреть, что система действительно течёт, сомневается и впадает в panic, любой другой стек обсуждает форму, а не идею. Если библиотека подтвердит концепцию, следующий горизонт скорее эмбеддинг и микроконтроллеры; конкретные инструменты к тому времени выбирать заново.

К октябрю 2026 этот прогон есть: синтетические сценарии в `tests/synthetic/`. DSL, Rust, бенчмарки и нейроморфное железо остаются отложенными.

## DR-020. У среднего измерений confidence весится, а не берётся как min

**Контекст.** Сценарий сети датчиков воздуха требует вес `1/σ²`: точный датчик важнее шумного. Арифметика `+` и `/` так не делает. Если к взвешенному среднему всё же применить `min` для confidence, датчик с огромным `σ` и низким confidence запретит итог, хотя на значение он почти не повлиял.

**Решение.** `weighted_mean` считает value и uncertainty по обратной дисперсии. Confidence — среднее confidence с теми же весами. `min` остаётся правилом для `+`, `-`, `*`, `/` (DR-016).

**Аргумент.** Это разные операции. Сложение переносит сомнение худшего звена, потому что оба слагаемых входят в результат целиком. В среднем независимых измерений шумное почти выпадает из суммы весов, и честность состоит в том, чтобы уверенность следовала за весом, а не за самым слабым прибором в списке.

## DR-021. Запасной режим только по явной паре

**Контекст.** После panic оркестратор на один цикл откатывает state в `fallback`, а следующий `tick` снова слушает вход. Если вход всё ещё плохой, panic повторяется. Сценарий палаты хочет другое: перейти на резервный датчик и держаться его.

**Решение.** Режим `degraded` включается в момент panic и дальше подменяет вход, но только когда заранее заданы оба поля: `backup_value` и `backup_noisy`. `recover()` выключает режим. Пара, заданная наполовину, режим не вооружает.

**Аргумент.** Самопроизвольное «я теперь в безопасном режиме» было бы скрытой политикой. Резервного датчика у оркестратора нет, пока его не назвали. Пока пара не задана, повторный panic — честное поведение: угроза не исчезла.

## DR-022. Классификация скачка не трогает confidence

**Контекст.** Сценарий воздуха отличает поломку одного датчика от облака, которое видят соседи. `weighted_mean` этому не помогает: если у вранья маленькая σ, вес как раз большой.

**Решение.** `classify_jump` отвечает `calm`, `alone` или `shared` и больше ничего не делает. Порог тот же, что у травмы: строго больше `trauma_threshold`.

**Аргумент.** «Это поломка, понизь ему доверие» — решение сценария, не закон русла. Библиотека показывает, один датчик дёрнулся или несколько. Насколько после этого раздуть uncertainty, задаёт вызывающий код.

## DR-023. Маски не крутятся вместе с panic сами

**Контекст.** У сущности может быть несколько имён: публичное, редакционное, имя для источника. При угрозе старые имена нужно убрать из всех ссылок сразу. Если это вшить в `SurvivalState._panic()`, любая тревога будет срывать маски, даже когда вызывающий код этого не просил.

**Решение.** Книга масок — отдельный объект `PolyphonicIdentity`. `erase` заменяет один хеш везде внутри книги. `rotate_all` делает это для всех масок. `SurvivalState` их не держит. Связка с panic — только callback, который сам вызывает `rotate_all`.

**Аргумент.** Стирание имени необратимо. Consent-First уже требует, чтобы такое действие было явной политикой. Книга, которую в callback не передали, остаётся при своих хешах: тревога в одном контуре не выжигает соседний.

---

## DR-024. Comfort реагирует на trauma и на спокойный шаг

**Контекст.** `comfort` жил на `FluxVar`, но только клипился в `[-1, +1]`. Синтетические сценарии задавали его снаружи, а trauma поле не трогала. Дорожная карта назвала это разрывом между идеей самочувствия и кодом.

**Решение.** При trauma comfort уменьшается на `trauma_comfort_cost` (по умолчанию `0.25`). При спокойном update растёт на `calm_comfort_gain` (по умолчанию `0.02`). Итог клипится. Нулевые ставки замораживают поле как раньше.

**Аргумент.** Скаляр из DR-004 полезен, только если движется вместе с руслом. Цена травмы и прирост спокойствия — параметры вызывающего кода, а не скрытая политика допустимых значений (DR-017 стоит). Нулевые ставки сохраняют старые тесты и старую ментальную модель.

## DR-025. Scope выбирает опциональный хук panic

**Контекст.** `scope` хранился и описывался в спецификации (`local` / `process` / `system`), но `_panic` делал одно и то же на любом масштабе: ротировал свой хеш и вызывал `on_panic`. Реальные эффекты (сброс соединений, ротация ключей) — дело приложения и должны оставаться Consent-First.

**Решение.** После общего `on_panic` `_panic` вызывает не больше одного из `on_panic_local`, `on_panic_process`, `on_panic_system` по значению `scope`. Отсутствующий хук — тишина. Библиотека по-прежнему не уничтожает данные и не крутит `PolyphonicIdentity` сама (DR-023).

**Аргумент.** Различать масштабы без opt-in политики — значит придумывать необратимые действия. Помеченный хук даёт сценарию назвать, что значит «process» или «system», а незаданный хук оставляет panic локальным для identity hash.

## DR-026. Стирание между книгами только через зарегистрированный ledger

**Контекст.** `PolyphonicIdentity.erase` видит одну книгу. То же мёртвое имя может сидеть в редакционной книге и в полевой. Спрашивать каждую книгу вручную легко забыть; вшивать глобальный ластик в `SurvivalState` — жечь книги, которые не соглашались.

**Решение.** `IdentityLedger` держит именованные книги, которые явно зарегистрировали. Его `erase` переписывает старый хеш во всех зарегистрированных книгах, где он есть, одним общим новым хешем. Книга без регистрации невидима. Неизвестный хеш → `KeyError`, ничего не меняется.

**Аргумент.** Снова Consent-First: видимость — это членство в ledger, а не «каждый объект в процессе». Один новый хеш сохраняет согласованность алиасов между контурами, которые сознательно делят имя.

## DR-027. Корреляция — явный аргумент weighted_mean

**Контекст.** Среднее с весом `1/σ²` предполагает независимость. Датчики, смотрящие в одно облако, коррелированы; считать их независимыми слишком сжимает σ и завышает confidence.

**Решение.** `weighted_mean(..., correlation=ρ)` при `ρ ∈ [0, 1]`. Веса значения остаются `1/σ²`. Uncertainty становится `σ_indep · √(1+(n−1)ρ)`. Confidence с ростом `ρ` тянется от взвешенного среднего к `min`. `ρ = 0` — прежняя формула.

**Аргумент.** Одно среднее попарное `ρ` — обычный способ признать зависимость. Когда у вызывающего кода уже есть полная матрица, дальше работает DR-029.

## DR-028. Scar Memory — opt-in, вне SurvivalState

**Контекст.** После сбоя то же место нужно сторожить внимательнее. Вшить усиление в `_panic` — навсегда ужесточить каждый контур, в том числе те, кто шрам не просил.

**Решение.** `ScarMemory` — отдельный объект. Вызывающий код помечает `site` (обычно из `on_panic` или `on_trauma`) и позже берёт `amplify(site, base)` для повышенной чувствительности. `fade` заживляет. Panic сам шрамы не пишет.

**Аргумент.** Шрам — политика бдительности, а не закон перерождения. Consent-First оставляет отметку явной; исследовательская идея «Scar Memory» становится проверяемым производным типом без смены фазового перехода panic.

## DR-029. Полная ковариация — опциональный путь GLS

**Контекст.** Скалярный `correlation` предполагает одно среднее попарное ρ. У реальных сетей датчиков часто уже есть ковариационная матрица; сжимать её в одно ρ — терять структуру.

**Решение.** `weighted_mean(..., covariance=Σ)` считает GLS-среднее: `μ = (1ᵀΣ⁻¹x)/(1ᵀΣ⁻¹1)`, `σ = 1/√(1ᵀΣ⁻¹1)`. Диагональ должна совпадать с `σ²` каждого измерения. `correlation ≠ 0` вместе с `covariance` отвергается. Точные измерения (`σ = 0`) с `covariance` недопустимы (вырождение). Confidence тянется к `min` по средней попарной корреляции, извлечённой из Σ.

**Аргумент.** Скалярный путь остаётся умолчанием. Матричный — opt-in честность для тех, кто уже измерил зависимость. Чистый Python-GLS не тащит зависимость от линейной алгебры в ядро.

## DR-030. Автопоиск живых книг — opt-in на вызове erase

**Контекст.** Стирание между книгами требовало либо регистрации (`IdentityLedger`), либо ручного обхода. Автопоиск по всему процессу без реестра раньше отклоняли как риск Consent-First: erase мог сжечь книги, которые в ledger не входили.

**Решение.** Каждый `PolyphonicIdentity` попадает в weak-реестр живых книг. `PolyphonicIdentity.live()` перечисляет достижимые. `erase_live(old_hash)` и `IdentityLedger.erase(..., discovered=True)` переписывают хеш во всех живых книгах, где он есть, одним новым. Обычный `ledger.erase` по-прежнему видит только зарегистрированные. Мёртвые объекты из weak-реестра выпадают.

**Аргумент.** Поиск не молчаливый: вызывающий код должен назвать `erase_live` или `discovered=True`. Регистрация остаётся безопасным умолчанием. Weak-ссылки не удерживают книги в памяти только ради реестра.
