# TRANSFLUX: Сценарии применения

> Четыре проработанных примера, показывающих,  
> как три оси TRANSFLUX работают вместе на конкретных задачах.

Сценарии ниже — постановка задачи. В библиотеке на октябрь 2026 из них уже есть: честное `NoisyFloat` и `gradient_of_truth`, русло `FluxVar`, panic и fallback, запасной датчик (`degraded`), среднее с весом `1/σ²`, отличие одиночного скачка от общего (`classify_jump`), несколько масок и стирание хеша внутри одной книги. Само не делается: развилка по `scope`, стирание хеша вне книги, автоматическое понижение confidence у одиночного скачка, таймер потери связи. Проверка на синтетике — `tests/synthetic/`.

## 1. Мониторинг пациентов в реанимации

### Боль классического подхода

Система снимает температуру, пульс, давление. Каждый показатель сравнивается с порогом: температура > 38.0°C → тревога. Просто. Но:

- **Шум игнорируется.** Датчик возвращает 38.1°C с реальной погрешностью ±2°C. Классическая система срабатывает на значении, которому нельзя доверять.
- **История не учитывается.** Температура 38.1 после стабильных 36.6 — это одно. Температура 38.1 после плавного роста с 37.0 за четыре часа — это другое. Классическая система не различает.
- **Ложные тревоги.** До 90% тревог в реанимации — ложные. Следствие: alarm fatigue — персонал начинает игнорировать сигналы, включая реальные.

### Как решает TRANSFLUX

**Value Model (NoisyFloat).**  
Каждое показание датчика — не число, а распределение: `NoisyFloat(38.1, uncertainty=2.0, confidence=0.4)`. Система знает, что доверие к этому значению — 40%. Gradient of truth для условия «жар» — около 0.35. Этого недостаточно для полной тревоги. Решение: запросить повторное измерение или переключиться на резервный датчик, а не поднимать ложный alarm.

**State Model (FluxVar).**  
Температура пациента — `FluxVar` с историей. Velocity = 0.32°C/час — это нормальное колебание (ниже trauma_threshold). Но если velocity скачет до 2°C/час — это аномалия, которую system фиксирует независимо от абсолютного значения. Тренд важнее точки.

**Survival Model (SurvivalState).**  
Если confidence трёх последовательных показаний падает ниже 0.3 — threat_level нарастает. При пересечении порога система входит в «degraded mode»: переключается на резервный датчик, уведомляет техника, маркирует все текущие данные как ненадёжные. Это не отказ — это управляемая деградация.

### Результат

| Метрика | Классика | TRANSFLUX |
|---|---|---|
| Ложные тревоги | ~90% | Снижаются: тревога пропорциональна confidence |
| Обнаружение трендов | Нет | Velocity / acceleration выявляют динамику |
| Реакция на сбой датчика | Нет данных → молчание или crash | Managed degradation через SurvivalState |

## 2. Автономный дрон в зоне с нестабильной связью

### Боль классического подхода

Дрон летит по GPS-маршруту. Контроллер следует точкам пути. Если связь потеряна — зависает или возвращается на базу. Но:

- **GPS врёт молча.** В городском каньоне точность падает с ±1м до ±15м. Контроллер не знает, что координаты ненадёжны — и выполняет манёвры по ложным данным.
- **Порывы ветра.** Резкий порыв → позиция «прыгает» → контроллер реагирует резкой коррекцией → раскачивание. Классический фильтр (Kalman) смягчает, но не осознаёт «травму».
- **Данные миссии.** При захвате дрона все данные маршрута, координаты базы и ключи связи — доступны.

### Как решает TRANSFLUX

**Value Model (NoisyFloat).**  
GPS-координата = `NoisyFloat(lat, uncertainty=σ_gps, confidence=f(число_спутников))`. В городском каньоне: 3 спутника → confidence = 0.3, uncertainty = 15м. Дрон автоматически увеличивает запасы безопасности (высота, дистанция до препятствий) пропорционально uncertainty — без изменения кода контроллера.

**State Model (FluxVar).**  
Позиция — `FluxVar` с velocity и acceleration. Порыв ветра → скачок velocity → trauma_threshold превышен → контроллер на N секунд переключается на инерциальную навигацию, игнорируя GPS-показания до стабилизации. Это фильтрация аномалий через физику состояния.

**Survival Model (SurvivalState).**  
Потеря связи с базой: каждые 5 секунд без пинга → threat_delta += 0.1. Через 10 секунд — threat ≥ threshold → panic: уничтожение точек маршрута, ротация ключей связи, переход в автономный безопасный режим. Физический удар (акселерометр показывает > 50g) → scope="system" → полная очистка данных.

### Результат

| Метрика | Классика | TRANSFLUX |
|---|---|---|
| Навигация при плохом GPS | Ложные манёвры | Расширение запасов ∝ uncertainty |
| Реакция на порыв | Раскачивание / Kalman | Trauma → инерциальный fallback |
| Данные при захвате | Доступны | Уничтожены через panic |

## 3. Защищённый мессенджер для журналистов

### Боль классического подхода

End-to-end шифрование (Signal protocol) защищает содержание сообщений в транзите. Но:

- **Метаданные открыты.** Кто с кем, когда, как часто — видно оператору и спецслужбам. Шифрование содержания не защищает идентичность.
- **Изъятие устройства.** Под принуждением пароль может быть вскрыт. Локальная база данных — улика. Даже с FDE (full disk encryption) существует окно уязвимости при разблокированном устройстве.
- **Нет аварийного протокола.** Пользователь должен вручную удалять чаты, выходить из аккаунтов, менять номер. На это нет времени в ситуации угрозы.

### Как решает TRANSFLUX

**Survival Model (SurvivalState).**  
Три триггера panic:
- *Кнопка тревоги* — одно нажатие;
- *Dead man's switch* — нет подтверждения статуса в течение N минут;
- *Duress-код* — специальный пароль, который выглядит как обычный, но активирует panic.

При panic (scope="system"):
- Ротация всех идентификаторов на всех связанных устройствах;
- Уничтожение локальной базы сообщений;
- Смена fingerprint устройства;
- Переход в «чистый» режим с пустым интерфейсом.

**Polyphonic Identity (производная от Survival).**  
Журналист имеет три слоя идентичности:
- Публичная персона (видна всем);
- Журналистский handle (виден редакции);
- Алиас для работы с источником (виден только источнику).

Каждый слой — отдельный identity_hash. Доказательство принадлежности к группе «аккредитованные журналисты» — без раскрытия того, какой именно журналист.

**Value Model (NoisyFloat).**  
Статус доставки сообщения: `NoisyFloat(delivered=1.0, uncertainty=0.2, confidence=0.7)`. Вместо обманчивой галочки «доставлено» — честный статус: «вероятно доставлено, подтверждение не гарантировано». Пользователь принимает решения на основе реального знания, а не иллюзии.

### Результат

| Метрика | Классика (Signal) | TRANSFLUX |
|---|---|---|
| Экстренная защита | Ручная | Один триггер → полная ротация |
| Защита идентичности | Номер телефона = идентификатор | Полифоническая: слои без outing |
| Честность статусов | «Доставлено» (бинарно) | Доставлено с confidence |

## 4. Сеть экологических сенсоров качества воздуха

### Боль классического подхода

200 датчиков PM2.5 по городу. Каждый шлёт показания раз в минуту. Центральный сервер усредняет → публикует индекс качества воздуха. Но:

- **Все датчики считаются равными.** Новый откалиброванный датчик и пятилетний с севшей батареей — одинаковый вес в среднем. Средний PM2.5 = 47 мкг/м³ может быть бессмысленным числом.
- **Спайк = паника.** Один датчик рядом с заводом показывает PM2.5 = 300. Реальный выброс? Или сбой датчика? Классическая система не знает.
- **Слепая зона.** Если 30% датчиков отключились (ночь, батареи, вандализм) — система всё равно публикует «индекс 47» с той же уверенностью. Пользователь не знает, что картина неполная.

### Как решает TRANSFLUX

**Value Model (NoisyFloat).**  
Каждый датчик отдаёт `NoisyFloat(pm25, uncertainty=f(age, calibration, battery), confidence=f(self_test))`.

Агрегация — не простое среднее, а взвешенная комбинация:
- Вес каждого датчика ∝ 1/uncertainty²;
- Хорошо откалиброванные датчики доминируют автоматически;
- Итоговый результат несёт собственную uncertainty и confidence.

**State Model (FluxVar).**  
Показания каждого датчика — `FluxVar` с velocity. Спайк PM2.5 = 300 → velocity превышает trauma_threshold. Система сравнивает с соседями:
- Соседние FluxVar тоже показывают рост velocity → вероятен реальный выброс, эскалация;
- Только один датчик «прыгнул» → вероятна неисправность, снижение его confidence.

Это пространственная корреляция через физику состояния, а не через отдельный алгоритм обнаружения аномалий.

**Survival Model (SurvivalState).**  
SurvivalState всей сети: агрегированный confidence всех датчиков. Если средний confidence падает ниже порога (слишком много датчиков offline / ненадёжны) — система публикует честный статус:

```
Индекс качества воздуха: 47
Достоверность: НИЗКАЯ
Покрытие: 68% датчиков
```

Это не отказ. Это управляемая честность.

### Результат

| Метрика | Классика | TRANSFLUX |
|---|---|---|
| Учёт качества датчиков | Все равны | Вес ∝ 1/uncertainty² |
| Обнаружение аномалий | Отдельный алгоритм | Velocity + пространственная корреляция |
| Честность при неполных данных | «Индекс 47» (молча) | «Индекс 47, confidence: LOW» |

## Общий паттерн

Во всех четырёх сценариях повторяется одна и та же структура:

1. **Классический подход** делает вид, что данные точны, состояние стабильно, а угрозы нет.
2. **TRANSFLUX** делает неопределённость, историю изменений и угрозу **явными и вычислимыми**.
3. **Emergent-поведение** возникает из взаимодействия осей: uncertainty порождает threat, velocity порождает threat, panic перезагружает state.

Это не три отдельных фичи. Это замкнутая система, которая умнее суммы своих частей.
