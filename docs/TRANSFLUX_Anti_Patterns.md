# TRANSFLUX: Anti-patterns

> Как **не** надо использовать TRANSFLUX.  
> Типичные ошибки и ловушки при работе с парадигмой.

---

## AP-01. Заворачивать всё в NoisyFloat

**Ошибка.** Применять NoisyFloat к значениям, которые точно известны:

```python
pi = NoisyFloat(3.14159, uncertainty=0.0, confidence=1.0)
```

**Почему это плохо.** NoisyFloat с `uncertainty=0` и `confidence=1.0` — это обычный float с лишними полями. Overhead есть, выигрыша нет. NoisyFloat имеет смысл, когда значение действительно несёт неопределённость: показания датчиков, результаты моделей, внешние данные.

**Правило.** Используй NoisyFloat только для значений, в точности которых есть сомнение.

## AP-02. Ставить trauma_threshold = 0

**Ошибка.** Установить порог травмы в ноль, чтобы «ловить все изменения»:

```python
flux = FluxVar(value=0.0, trauma_threshold=0.0)
```

**Почему это плохо.** Любое ненулевое обновление вызывает trauma callback. При высокой частоте обновлений (IoT, streaming) это генерирует тысячи ложных сигналов в секунду — аналог alarm fatigue из медицины.

**Правило.** trauma_threshold должен отражать реальный порог аномалии для конкретного домена. Если не знаешь, какой ставить — начни с медианы ожидаемых velocity.

## AP-03. Использовать panic как control flow

**Ошибка.** Намеренно вводить систему в panic для «перезагрузки»:

```python
survival.update(threat_delta=1.0)  # force panic to "reset"
```

**Почему это плохо.** Panic — это **аварийный** фазовый переход для ситуаций реальной угрозы. Он ротирует identity_hash (криптографически дорого), сбрасывает state, инкрементирует panic_count. Использование его как аналога `restart()` — злоупотребление, которое:
- затирает identity без причины;
- делает panic_count бессмысленным;
- отучает систему (и разработчика) различать «нормальный сброс» и «реальная угроза».

**Правило.** Для нормального сброса используй `flux.update(initial_value)` и `survival.threat_level = 0`. Panic — только для настоящего panic.

## AP-04. Игнорировать confidence при принятии решений

**Ошибка.** Использовать `NoisyFloat.value` без проверки `confidence`:

```python
if sensor.value > threshold:  # bad: confidence ignored
    activate_alarm()
```

**Почему это плохо.** Это уничтожает смысл NoisyFloat. Вся парадигма Value Model строится на том, что решения масштабируются доверием. Бинарное сравнение — возврат к классике.

**Правило.** Используй `gradient_of_truth()` или явную проверку confidence:

```python
if sensor.gradient_of_truth() > 0.7:
    activate_alarm()
# или
if sensor.value > threshold and sensor.is_reliable():
    activate_alarm()
```

## AP-05. Связывать оси без orchestrator-а

**Ошибка.** Вызывать `survival.update_from_flow(flux)` из callback-а самого FluxVar, создавая рекурсию:

```python
def on_trauma(flux, velocity):
    survival.update_from_flow(flux)       # может вызвать panic
    if panicked:
        flux.update(survival.fallback)    # вызывает update → может снова вызвать on_trauma
```

**Почему это плохо.** Циклические вызовы, потеря контроля над порядком обновлений, невоспроизводимое поведение.

**Правило.** Используй паттерн orchestrator (TransfluxSystem или явный цикл). Callbacks — для логирования и уведомлений, не для мутаций состояния.

## AP-06. Забывать про decay_rate

**Ошибка.** Оставить `decay_rate = 0` в долгоживущей системе, не осознавая последствий.

**Почему это плохо.** При `decay_rate = 0` threat_level монотонно растёт. Любая система с ненулевой uncertainty **гарантированно** войдёт в panic — вопрос только времени. Для тестов это нормально, для продакшена — часто нет.

**Правило.** Осознанно выбери decay_rate для своего контекста:
- 0 — для параноидных систем (сообщение, криптография);
- 0.01–0.05 — для устойчивых систем (мониторинг, IoT);
- подбирается экспериментально — нет универсального значения.

## AP-07. Путать Panic-First с Consent-First

**Ошибка.** Считать, что Panic-First означает «уничтожай данные при любой тревоге».

**Почему это плохо.** Panic-First — принцип **приоритетов**: выживание > целостность. Consent-First — принцип **API**: деструктивные действия требуют явной политики. Они не противоречат друг другу:

- Panic-First говорит: *если выбор между потерей данных и потерей системы — потеряй данные*.
- Consent-First говорит: *этот выбор должен быть явно сконфигурирован разработчиком, а не сделан по умолчанию*.

**Правило.** Всегда настраивай `fallback`, `scope` и политику уничтожения данных **до** того, как система может войти в panic.

## AP-08. Делать uncertainty вручную вместо propagation

**Ошибка.** Вычислять uncertainty результата вручную вместо использования операций NoisyFloat:

```python
result_value = a.value + b.value
result_uncertainty = a.uncertainty + b.uncertainty  # wrong formula!
```

**Почему это плохо.** Формула `σ_a + σ_b` — это верхняя граница, не точное значение. Правильная формула — `√(σ_a² + σ_b²)`. Ручное вычисление обходит propagation и вносит ошибки.

**Правило.** Работай с NoisyFloat как с типом. Используй операторы `+`, `-`, `*`, `/`. Если нужна нестандартная операция — вычисляй propagation через частные производные.

---

## Мета-правило

> Если ты используешь TRANSFLUX, но делаешь `.value` на каждом шагу,
> чтобы получить «обычный float» — ты используешь TRANSFLUX неправильно.

Ценность парадигмы — в том, что uncertainty, history и threat **передаются** через всю цепочку вычислений. Каждый `.value` — это точка, где эта информация отбрасывается.
